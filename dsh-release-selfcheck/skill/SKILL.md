# 发布自检（Release Self-Check）

**目的**：在东西发出去**之前**，把「不该发的发出去了」「该发的没发成」「发了但没人能下」这三类问题挡住。

**与合规审核 skill 的分工**：
- 本 skill = **东西对不对**（产物、版本、架构、链接、发布纪律）
- 合规 skill = **话能不能说**（对外文案的合规红线）
- 两者都要跑，**不能互相替代**

**适用范围**：任何"构建产物 → 分发到多个渠道（应用商店/对象存储/CDN/GitHub Release）"的发布流程。桌面客户端（Electron 等）尤其适用。

---

## 零、为什么需要它（真实事故，不是假设）

以下每一条都实际发生过，且**当时所有 CI job 都是绿的、日志里没有任何异常**：

| 事故 | 表面现象 | 真实后果 |
|---|---|---|
| 迁移脚本的临时目录叫了 `assets`，撞上仓库已有的 `assets/` | 工作流"成功" | 把 11 个无关的网站图片一起传上了对象存储 |
| 两个 macOS job 的 artifact 同名（都用了 `matrix.os`） | 四个 job 全绿 | macOS arm64 **整个丢失**，该平台用户没得下载 |
| 用 `unzip -l` 的输出做断言，把完好的包判成坏包 | 构建"失败" | 正确产物被拦下，排查方向被带偏 |
| 命令行参数 `--key=value` 不被解析器支持 | 脚本打印"无需处理"、退出码 0 | 阈值静默丢失，该做的一件没做 |
| 改一个 JSON 字段时整段配置被顺手删掉（签名相关） | 构建成功 | 打出签名无效的包，只影响其中一个平台 |
| 验证步骤用 `curl -o /dev/null` 而非 `-I` | 看起来在"验证" | 几个 GB 白下载，白等十几分钟 |

**共同点：都是「没有报错但事情没做成 / 做错了」。**
所以本 skill 的核心不是"看有没有报错"，而是**逐个断言可核对的最终结果**。

## 一、三条铁律

### 铁律 1：断言「结果」，不要断言「过程」

| ❌ 不要这样断言 | ✅ 要这样断言 |
|---|---|
| 函数返回了 `changed=true` | **目标文件里到底有没有那段内容** |
| 所有 job 都 success | **产物清单里每个平台在不在** |
| 命令 exit 0 | **HTTP 状态码是不是 200**（用 `-I`） |
| 日志里没报错 | **下载回来的哈希与原件一致** |

**并且：判据要对着「应该是什么」，不能对着「手里有什么」。**
验证器与上传器的过滤规则必须同源 —— 否则会出现"上传器刻意跳过某类文件，
验证器却拿整个目录去核对"，于是报出假失败。

### 铁律 2：只上传「显式清单」，不上传「某个目录的全部内容」

这是"多传了 11 个无关文件"那次事故的根因。**目录内容会变，清单不会。**

```bash
# ❌ 危险：目录里多出什么就传什么
upload --dir some-dir

# ✅ 安全：先比对清单，一致了才传
bash <selfcheck.sh 路径> manifest expected.txt ./实际目录
```

**并且**：给上传/下载用的临时目录起名时，**先确认仓库根目录没有同名目录**：

```bash
ls -d "$(git rev-parse --show-toplevel)"/assets dist build public static
```

### 铁律 3：先自检环境与权限，再验业务逻辑

把「权限/凭据/端点」和「业务是否正确」**分开验证**。
否则一旦失败，你无法判断是环境问题还是逻辑问题，排查时间成倍增加。

## 二、检查清单（按顺序，逐项打勾）

### A. 产物清单（最容易被忽略的一步）

- [ ] 拿到**预期清单**（下载页实际引用哪些文件 × 哪些平台）
- [ ] 拿到**实际清单**（准备上传/已上传的文件）
- [ ] 两者**逐一比对**：多一个要问为什么，少一个要问为什么
- [ ] 特别确认没有混入仓库自身的资源（`icons/`、`pets/`、`contact-*` 等）

```bash
bash <selfcheck.sh 路径> manifest expected.txt ./实际目录
```

### B. 版本一致性

- [ ] 包清单里的 version == 即将打的 tag == 产物文件名里的版本
- [ ] **所有对外站点**的版本号一致（不一致会出现"从首页点下载拿到旧版"）
- [ ] 各产品线（主程序 / 配套客户端 / 套装包）有**各自独立**的版本号，
      **不要被主程序的版本批量覆盖**（批量替换脚本必须按产品族锚定）

```bash
bash <selfcheck.sh 路径> versions
```

### C. 平台与架构（**不能只看文件名**）

- [ ] 每个目标平台的产物都在
- [ ] 同一平台的多架构版本**内容真的是对应架构**（解包看二进制头，不是看文件名）
- [ ] 随包载荷（嵌入的解释器/运行时/资源）的架构与包架构**一致**
      —— 否则会出现"装得上、用不了"
- [ ] 大文件不是空包（条目数 + 体积下限）

```bash
# macOS：主可执行文件的架构
file "<解包路径>/X.app/Contents/MacOS/X"
# 随包载荷清单里的架构标记
python3 -c "import zipfile,json,sys; z=zipfile.ZipFile(sys.argv[1]); n=[x for x in z.namelist() if x.endswith('runtime.json')][0]; print(json.loads(z.read(n)))" 包.zip
```

### D. 上传内容过滤

- [ ] 官网/下载页**不提供**的格式（如仅用于自动更新的 `.zip`、`.blockmap`、
      增量元数据 `latest*.yml`）**不要上传**
- [ ] 但**同名不同用途**的文件别一刀切排掉（例如"套装 .zip"是要上传的，
      "桌面端 .zip"不是）—— 过滤规则要按**完整路径**匹配，不能只按扩展名
- [ ] 上传目标目录里**没有**仓库自身的资源文件

### E. 站点上线前

- [ ] 从**线上页面**抽取全部下载链接（不是从本地文件）
- [ ] 每个链接 `curl -I` 实测 **200**（403 = 源站没有该对象；000 = 网络抖动需重试）
- [ ] 版本徽标、平台数标签与实际产物一致
- [ ] 部署后**再验一次**（部署可能没生效或有缓存）
- [ ] 跨站一致性：多个站点（主站 / 静态托管站）指向的版本与目标 tag 一致

```bash
bash <selfcheck.sh 路径> links <页面URL>
```

### F. 发布纪律

- [ ] 主程序的 Release 是**正式版**（非 Draft、非 Pre-release）→ 才会成为
      "latest"，自动更新才生效
- [ ] 🔴 **附加发布（套装/合集）必须标记为 Pre-release** ——
      不标记会抢走 "latest"，让主程序的自动更新**静默失效**
- [ ] "latest" 指向的是**主程序**，不是附加发布
- [ ] Draft 转正式之后，确认在发布列表里确实可见

```bash
bash <selfcheck.sh 路径> release v1.0.19 suite-v1.0.19
```

### G. 对外内容合规

- [ ] 跑合规审核 skill 的线上扫描，**零命中**
- [ ] 改过 release notes / README / 页面文案时，本地也要扫一遍

### H. 现场与清理

- [ ] GUI 测试的进程**全部回收**（Electron 的子进程不会跟父进程一起死，
      只 `kill` 父进程会留下几十个孤儿进程）
- [ ] 临时目录、下载回来的验证包已清
- [ ] **不误删别人的文件**：清理只用**精确路径**，**不用宽通配符**
      （`/tmp/fix*` 会误伤别人的 `fix_bypass.py`）
- [ ] 用户正在用的服务未受影响（例如本地开发端口仍应正常响应）

## 三、已知假阳性（**不要误伤**）

跑检查时下列命中是**正常的**，不要为此改代码或改文案：

### 合规扫描类
- 合规插件**自身**的文件（README / SKILL.md / 词表实现）—— 里面列的就是违禁词本身
- 依赖锁文件里的 `VPN` 等词 —— base64 哈希里的巧合
- CSS 的 `绝对定位`、代码注释里的 `永远不执行`
- CI 工作流注释里的技术表述、CHANGELOG 里"去掉某某绝对化表述"这类**自指**句子

### ⚠️ 本 skill 的正文**自身**会命中扫描 —— 这是预期的，不要改正文

「已知假阳性」这一节必须**逐字引用**那些词（`VPN`、`绝对定位`、`永远不执行`）
才能说清楚哪些不该报。所以拿合规扫描去扫**本包自己**，一定会有命中 ——
那是文档在解释规则，不是内容违规。**不要为了"扫干净"去改这一节。**

### 本 skill 类
- 下载目录里出现 `.blockmap` / `latest*.yml` 是**正常的** ——
  它们在 Release 里有，只是不该上传到下载站。
  **比对要按"上传清单"比，不是按"Release 资产清单"比**
- 版本号不一致但正在准备下一版时属正常 —— 检查项会提示为"提示"而非"失败"

## 四、命令速查

```bash
bash <selfcheck.sh 路径> config                          # 看当前配置与自动推断结果
bash <selfcheck.sh 路径> manifest expected.txt ./dir     # 产物清单比对（核心）
bash <selfcheck.sh 路径> versions                        # 版本一致性
bash <selfcheck.sh 路径> links <页面URL>                  # 线上链接逐条 HEAD
bash <selfcheck.sh 路径> release <主程序tag> [套装tag]     # 发布纪律
```

**配置**（全部可选，不设则自动推断）：

| 环境变量 | 说明 | 默认 |
|---|---|---|
| `SELFCHECK_REPO_DIR` | 仓库根目录 | 从当前目录向上找 `package.json` |
| `SELFCHECK_REPO_SLUG` | 仓库 slug（`owner/repo`） | 从 `git remote origin` 推断 |
| `SELFCHECK_MAIN_SITE` | 主站目录（用于跨站版本比对） | 不设则跳过该项 |
| `SELFCHECK_PAGES_INDEX` | 静态托管站的 index 路径 | `<repo>/docs/index.html` |

```bash
SELFCHECK_MAIN_SITE=/path/to/main-site bash <selfcheck.sh 路径> versions
```

## 五、出问题时的排查顺序

1. **先确认判据本身对不对** —— 判据错了会把正确的东西判成错的，把你带偏
2. **再确认清单** —— 是"东西不对"还是"我比对错了"
3. **再确认版本/架构** —— 文件名对不代表内容对
4. **最后才怀疑业务逻辑**

供参考的具体取值，其它项目按自己情况替换：

```bash
export SELFCHECK_REPO_DIR=/Users/mac/dsh-desktop
export SELFCHECK_MAIN_SITE="/Users/mac/DeepSeek Harness/site-migration/deepwhale.org.cn"
# 仓库 slug 会自动从 git remote 推断为 feely0208/deepwhale-desktop
```

日常三条命令：

```bash
bash <selfcheck.sh 路径> versions
bash <selfcheck.sh 路径> links https://deepwhale.org.cn/download.html
bash <selfcheck.sh 路径> release v1.0.18 suite-v1.0.18
```
