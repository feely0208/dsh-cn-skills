# 密钥与敏感信息扫描

在**提交前**和**发布前**，把代码里不该出现的密钥、令牌、私钥、内部信息找出来。

它是这一组技能里唯一**通用**的（不限中国大陆）—— 因为"密钥进了仓库"是所有技术团队都会踩的坑。

## 一、何时用

- 提交前（可作为 pre-commit / CI 卡口，脚本有退出码）
- 开源前、发布前、把仓库转公开前
- 交接、离职、外包交付时做一次清点
- 怀疑泄露后做排查（此时**第一件事是轮换，不是删代码**）

## 二、先跑脚本

```bash
<scan.sh 路径> --dir /path/to/repo
```

它扫六类：高置信令牌（云厂商 AK、GitHub/npm/Slack 令牌、Google API Key）、私钥与证书文件、
凭据文件是否被 git 跟踪、配置里的敏感赋值、内网 IP 与内部域名。

**退出码：1 = 有高置信命中**，可以直接挂到 pre-commit 或 CI 上。

> ⚠️ 输出**默认打码**（只留前后几位）。扫描工具把完整密钥打进终端或日志，
> 等于换个地方又泄露一次。要看全必须显式加 `--reveal`，且**别把输出存进文件或贴进聊天**。

## 三、处置顺序（**这一节比扫描本身更重要**）

```
1. 轮换   →  2. 清理   →  3. 判断是否需要改写历史
```

### 1. 先轮换（作废旧的）

**凡是真的密钥，第一件事是去服务商后台把它作废并签发新的。**

为什么必须先做这步：删代码**不会**让已经泄露的密钥失效。它还在：

- git 历史里（`git log -p` 一搜就有）
- 已经推送到远端的副本里（fork、clone、镜像）
- CI/CD 的构建日志与缓存里
- 你本机的 shell 历史、编辑器备份、临时文件里

> 判断标准：**这个密钥有没有离开过你的机器？** 离开过（推过、构建过、贴过），就当已泄露。

### 2. 再清理代码

- `git rm --cached <file>` 把凭据文件移出跟踪（保留本地文件）
- 补 `.gitignore`（`.env`、`*.pem`、`.npmrc` 等）
- 改成从环境变量读取，并补一份 `.env.example`（只放占位符）

### 3. 最后决定要不要改写历史

`git filter-repo` 可以重写历史，但：

- **已经泄露的密钥即使改写历史也仍然算泄露**（别人可能已经 clone 过）→ 所以第 1 步不能省
- 改写历史会影响所有协作者（需要重新 clone），团队仓库要谨慎

## 四、误报怎么处理

扫描的召回和误报是矛盾的。本工具的做法是：

| 情况 | 处理 |
|---|---|
| 文档里的示例值（`your-api-key-here`、`sk-example-...`） | **已自动过滤**（脚本内置占位符名单） |
| 测试用的假密钥 | 建议改成明显的假值（含 `example` / `dummy`），这样也会被自动过滤 |
| 真的密钥 | 按第三节处置 |
| 拿不准的 🟠 | 打开文件看一眼上下文；**别因为误报多就不看报告了** —— 那正是这类工具失效的方式 |

## 五、与相邻技能的边界

- `dsh-cn-compliance` 的 I 类管**内部文件公网暴露**（被搜索引擎/公开链接读到）
- 本技能管**内部信息进了代码仓库**（该不该提交、提交了怎么补救）
- 两者的交集是"内部信息"，但一个看**暴露面**，一个看**版本控制**

## 六、纪律

- **不要把扫描输出当证据保存**。默认打码就是为此；需要留档时只记文件名与行号。
- **不要用"删掉了"当结论**。见第三节第 1 条。
- **不是所有命中都要慌**。先判断真假、再判断有没有离开过本机。
- **扫描只覆盖已知模式**，"没扫到"不等于"没有"（例如自定义格式的令牌）。
