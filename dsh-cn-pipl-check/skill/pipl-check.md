# 个人信息保护合规 · 声明 ↔ 实现对照

本技能回答一个具体问题：

> **隐私政策里承诺的，和代码里真做的，是不是一回事？**

它不管"话怎么说"（那是 `dsh-cn-compliance` 的事），只管**说的和做的是否对得上**。
应用市场驳回的第一大原因不是文案写错，而是这两者对不上。

## 一、何时用

- 准备提交应用市场（华为 / 小米 / OPPO / vivo / 应用宝）之前
- 上线或改版隐私政策之后
- 新增权限、接入新 SDK、新增数据上报之后
- 用户问「你们收集了我的什么」而你需要一份能对着代码讲的清单时

## 二、先跑扫描脚本（只取证，不定性）

```bash
# 扫当前目录
<scan.sh 路径>

# 扫指定目录
<scan.sh 路径> --dir /path/to/app

# 加上「政策 ↔ 代码」对照（推荐）
<scan.sh 路径> --dir /path/to/app --policy /path/to/privacy.md
```

脚本会输出七段**事实**：工程识别、权限、第三方 SDK、用户权利入口、出站域名、隐私政策定位、对照。
它**不判违规** —— 判定是人和审核方的事。

> ⚠️ 脚本是取证工具，**退出码 0 不代表合规**。找不到某项 ≠ 不存在（可能叫别的名字、或在服务端）。

## 三、六个必查项

### 1. 权限是否「最小必要」

对每一个权限，回答三个问题：

| 问题 | 不合格的样子 |
|---|---|
| 有没有**非它不可**的功能？ | 一个纯工具类 App 申请通讯录 |
| 申请**时机**对不对？ | 一启动就弹一串权限，用户还不知道你要干什么 |
| 有没有**说明用途**？ | 弹窗只有"允许/拒绝"，没有"用于 XX" |

> 判定口径：**不给这个权限，核心功能还能不能用？** 能，就不该要。

### 2. 第三方 SDK 清单是否与政策一致

政策里通常有一段「我们接入的第三方 SDK」，列出名称、收集的信息、用途。
**它必须和打包里真实存在的 SDK 一致。**

常见不一致：接了个统计 SDK 忘了写；写了的 SDK 其实已经删掉；写了 3 个实际有 6 个。

### 3. 用户权利入口是否真能走通

《个人信息保护法》给了个人五项权利，**必须有可被用户操作的入口**：

| 权利 | 实现形态 | 常见缺失 |
|---|---|---|
| 查阅、复制 | 「导出我的数据」 | 只在政策里承诺，App 里没有 |
| 更正、补充 | 个人资料页可改 | —— |
| **删除** | 删除单条数据 | 只支持删账号，不支持删数据 |
| **注销账号** | 明确入口（多在「设置 → 账号」） | **最常缺**：政策写了，代码里找不到 |
| 撤回同意 | 关闭个性化推荐 / 关闭权限 | 关了但没生效 |

> ⚠️ 注销账号**必须能自助完成**。要求"发邮件申请"在多数市场的审核口径里不算合格。

### 4. 敏感个人信息是否「单独同意」

以下属于敏感个人信息，**必须单独弹窗取得同意**，不能混在总协议的一键同意里：

- 生物识别（人脸、指纹、声纹）
- 行踪轨迹（持续定位、后台定位）
- 医疗健康
- 金融账户
- 不满十四周岁未成年人的信息（**还需取得监护人同意**）

自检：这类信息在代码里是**单独询问**的，还是跟着首次启动的总协议一起"被同意"掉的？

### 5. 数据是否出境

把扫描出的域名与服务商逐个过一遍：服务器在境内还是境外？
若涉及出境，政策里必须说明，且可能触发**单独同意 + 安全评估**。

### 6. 政策里的承诺能否逐条落到实现

把政策中所有**具体承诺**摘出来做成清单，逐条找实现：

- 「我们不会向第三方共享」→ 有没有 SDK 在上报？
- 「数据保存 3 年后删除」→ 有没有删除逻辑？
- 「您可随时撤回同意」→ 撤回入口在哪？
- 「我们使用加密传输」→ 是不是真的 HTTPS？

## 四、输出格式

```markdown
# 个人信息保护合规对照 · <产品> · <日期>

## 结论
- 权限：N 项，M 项未在政策中体现
- 第三方 SDK：代码里 X 个，政策里写了 Y 个
- 用户权利入口：注销 ✅ / 导出 ❌
- 敏感信息单独同意：位置 ⚠️ 混在总协议
- 数据出境：未发现 / 发现 N 处

## 对照明细
| 项 | 代码里的事实（文件:行） | 政策里怎么写的 | 结论 |
| --- | --- | --- | --- |
| ACCESS_FINE_LOCATION | AndroidManifest.xml:12 | 未提及 | 🔴 不一致 |
| 账号注销 | 未找到入口 | 「可随时注销」 | 🔴 缺实现 |
| 友盟 SDK | build.gradle:88 | 未列 | 🟠 需补 |

## 需人工判断
- …（脚本与规则覆盖不到，或需要产品/法务确认的）

## 已修复
- …
```

## 五、修复原则

1. **先说清楚，再改代码**：不一致有两种修法 —— 改代码去满足承诺，或改承诺去匹配实现。
   **优先改代码**（承诺是给用户的），但确实做不到的要如实改承诺。
2. **权限能删就删**：最小必要不是"写了说明就行"，是用不到就别要。
3. **别用"已获得用户同意"当挡箭牌**：同意必须建立在**充分告知**之上；
   混在总协议里的同意，在单独同意场景下不成立。
4. **改动要留痕**：政策改了要更新版本号与生效日期，App 内弹窗让用户重新确认。

## 六、纪律（重要）

- **只报事实、不下法律结论**。说「代码里有 X 权限，政策未提及」，
  不说「你违法了」—— 定性由法务和审核方做。
- **找不到 ≠ 没有**。脚本搜不到"注销"两个字，可能只是叫法不同。
  报「未找到入口」时必须带上这句话。
- **不内置敏感数据**。本技能只做事实比对，不涉及任何个人数据样本。
- **与相邻技能的边界**：
  - `dsh-cn-compliance` 管**话怎么说**（文案红线）
  - `dsh-cn-ai-labeling` 管**AI 生成链路**的标识
  - 本技能管**隐私相关的声明与实现是否一致**
